Short answer

A web crawler takes URLs from a frontier, fetches them, and stores the responses it was able to read.

The diagram shows that pipeline: a frontier of addresses, fetchers, and storage. It is a map of parts, not a ranking system and not a trace of this site. SEO Health asks whether your important URLs can enter that kind of pipeline: a status that returns the document, a robots rule that allows the fetch, and a link or sitemap entry that put the URL on a frontier in the first place.

Definition

Fetching is not the same as understanding. A stored response that is a shell, a 403, or a 500 is a stored failure. The architecture diagram does not promise that every box runs for every site, and this article does not invent a crawl budget or a coverage percentage. The practical reading is the sample URL: what a clean fetch returns, and which page linked to it.

How a crawl meets this rule

Give important documents a URL a fetcher can request, and a link that can place it on a frontier.

A sitemap can add URLs to the work list. It does not replace the link, and it does not repair a 500. Storage of the response is the crawler’s concern. Your concern is that the response is the document. Re-fetch a sample after a template change instead of assuming the diagram’s storage box updated itself.

What to check

  • A sample URL that returns the document
  • A link or sitemap entry that can enqueue it
  • Robots rules that allow that fetch
  • Failures recorded as status codes, not as missing topics
  • A re-fetch after the template change

A practical example

A new specification exists only as a button that loads it into the current page. No URL is fetched, so no frontier can hold it. The repair publishes a URL that returns the specification and links it from the product page. The architecture diagram stays a general map. It is not a log of that product URL.

What this does not claim

Being fetchable does not guarantee rankings or citations.
