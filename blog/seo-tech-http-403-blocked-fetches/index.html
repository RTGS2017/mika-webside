A 403 Means the Server Refused the Fetch

A 403 status means the server understood the request and refused to fulfill it.

Short answer

A 403 status means the server understood the request and refused to fulfill it.

That is different from a 404, which says the target is not there, and from a 401, which asks for authentication. A product URL that returns 403 to a crawler and 200 to a browser with cookies is a discovery failure for anyone who does not send those cookies. SEO Health fetches without the staff cookie and records the status.

Definition

A firewall rule that blocks unfamiliar user-agents can create this pattern after a security change. The health decision is which agents must be allowed to fetch the public site. Private admin URLs should keep refusing. The public canonical URLs should not. The screenshot is a plain Forbidden page: the words a person sees. It is not a vendor’s product and not a score.

How a crawl meets this rule

Fetch public canonical URLs without a logged-in cookie and confirm they are not 403.

If a 403 page is styled and returns 403, the status is honest. If it returns 200, you have a soft error on top of a block. Fix the status and the rule that blocks the public fetch. Do not add the 403 URL to the sitemap to “help” it.

What to check

  • Public URLs fetched without staff cookies
  • 403 reserved for paths that should be private
  • Block pages that return 403 rather than 200
  • Sitemaps free of refused URLs
  • One sample URL re-fetched after the rule change

A practical example

After a bot filter, /products/valve returns 403 to a normal crawler fetch and 200 in the marketing team’s browser. The filter’s allow list gains the public paths. The admin path stays 403. A second fetch without cookies confirms the valve URL. No ranking claim is attached to the firewall vendor.

What this does not claim

Removing an accidental 403 does not guarantee rankings or citations.
