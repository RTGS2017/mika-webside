An Ajax Call Is Not a Link a Crawler Can Follow From HTML

Ajax fetches data after the page has loaded. It does not, by itself, give a crawler a URL to follow.

Short answer

Ajax fetches data after the page has loaded. It does not, by itself, give a crawler a URL to follow.

The comparison figure shows a full document load beside a partial update. People can prefer the partial update. Discovery still needs the document. If the partial update contains the only copy of a product list, that list is not in the fetched HTML. SEO Health asks for URLs whose GET response includes the list, with anchors to them.

Definition

History API addresses that do not have a server response are bookmarks to a state, not documents. A crawler that only fetches will not replay the Ajax sequence that built the state. Do not point the sitemap at those addresses unless a GET returns the document.

How a crawl meets this rule

Give each discoverable set a URL that returns it, and use Ajax only as an enhancement of that URL.

A filter that requests /api/parts and paints the result can keep doing so for people if /parts?family=gate already returns the same items in HTML and is linked. The API is not the crawl path. The HTML URL is.

What to check

  • GET URLs whose HTML contains the items Ajax would have loaded
  • Anchors to those URLs in the initial HTML
  • History addresses that actually return the document
  • APIs not listed in the sitemap as if they were pages
  • One paged URL fetched without running script

A practical example

The catalog’s “load more” button calls an endpoint and appends cards. There is no second URL. The repair adds the paged URL, puts the anchors in the first page’s HTML, and lets the button fetch that same URL if you still want the gesture. The endpoint can stay private to the button.

What this does not claim

Ajax enhancements do not guarantee rankings or citations.
