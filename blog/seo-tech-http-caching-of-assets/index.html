Short answer

HTTP caching lets a repeat request reuse a stored response or revalidate it with a short 304.

The diagram shows a 304: the client asked, the server said the bytes have not changed, and the body was not sent again. That helps assets whose URLs change when the file changes. It is the wrong policy for HTML if a long-lived cache hides an update you needed crawlers and buyers to see. SEO Health separates the HTML policy from the asset policy.

Definition

A fingerprinted stylesheet can be cached for a long time because the next version has a new URL. The HTML that points at that URL should be revalidated so the new fingerprint is discovered. Caching everything “for a year” because a slider said so is how product pages go stale. The 304 figure is an illustration of revalidation, not a hit rate for any company.

What rendering changes for a crawler

Cache fingerprinted assets for a long time, and revalidate HTML so new asset URLs are discovered.

Personalized HTML that includes a name or a cart should not be stored in a shared cache. A public product document usually should be cacheable with revalidation. The audit sample is the response headers of one HTML URL and one hashed asset, not a single max-age pasted onto both.

What to check

  • Long cache on fingerprinted assets only
  • HTML revalidated so new fingerprints are seen
  • Personalized HTML kept out of shared caches
  • Headers sampled on one HTML URL and one asset
  • No single max-age applied to every response

A practical example

A deploy fingerprints app.js but the HTML is cached for a day without revalidation, so visitors and crawlers keep the old HTML that points at a deleted file. The health fix shortens or revalidates the HTML cache and leaves the long cache on the fingerprinted file only.

What this does not claim

Cache headers do not guarantee rankings or citations.
