A CDN Serves the Response. It Does Not Rename the Document

Short answer

A CDN stores copies of responses and answers from them. The document’s URL stays the one you canonicalized.

The figure draws the contrast. On the left, clients reach one origin. On the right, clients reach several servers in a cloud. Both pictures are about where the bytes come from. Neither picture is a latency score, and this article does not invent one. SEO Health asks whether the copy a client receives is the same document: same canonical, same primary text, same links.

Definition

HTML that is assembled differently at the edge, for example by injecting a region into the H1 based on the client address, creates variants that do not match the canonical. Static assets can move to the CDN more safely than the document’s meaning. A stale edge copy that still serves an old canonical after you changed the template is a cache problem, not a new page. Purge or version the URL of the asset. Do not publish a second document to escape a stale copy.

What rendering changes for a crawler

Keep one canonical HTML document, and use the CDN as a copy of that response or of its assets.

Check a fetch of the canonical URL and, if you can, a fetch that is served from the edge. The primary text should agree. Cache keys that include cookies can split the document into private copies. Public pages should be cacheable without a session. The right-hand cloud in the figure is not permission to vary the H1.

What to check

  • One canonical URL for the HTML document
  • Edge copies that keep the same primary text
  • Public HTML cached without a session cookie
  • Asset URLs versioned or purged when they change
  • Two fetches of one product URL that agree

What this does not claim
