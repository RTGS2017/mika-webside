Short answer

RDFa annotates existing HTML with types and properties.

typeof and property attributes name a thing and its fields in the document. The health rule is the same as for microdata and JSON-LD: the field must be the fact the element shows, and two syntaxes on one page must not disagree. RDFa is not a GEO method and not a ranking method. It is a technical encoding.

Definition

Prefixes and vocabularies make RDFa look more abstract than a product page needs. If the template cannot be reviewed by the person who edits the product name, the encoding will drift. Prefer one syntax the team can actually read. The pie charts are a historical picture on the source page. This article does not adopt their labels as a measurement for any site.

What the markup can and cannot do

Keep one syntax, and make every RDFa property match the visible text on that element.

Copying an RDFa example from a vocabulary page without the matching sentences produces a page that claims a type it does not explain. The audit fails that page for the mismatch, not for the choice of letters in the attribute name.

What to check

  • One syntax on the page
  • Property values equal to the visible cells or headings
  • Types the prose actually explains
  • A reviewer who can read the template
  • One documentation URL compared cell by cell

A practical example

A documentation page uses RDFa to mark a specification table and JSON-LD that names a different unit for the same pressure value. The repair deletes one syntax and makes the remaining value equal the table cell. The unit is a fact. The syntax is not allowed to invent a second unit.

What this does not claim

RDFa does not guarantee rankings, rich results, or citations.

Where Mika Visibility files this
