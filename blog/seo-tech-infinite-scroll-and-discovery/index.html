Infinite Scroll Hides Later Items Unless They Have URLs

Infinite scroll loads later items into the current page as the visitor moves, and those items have no URL of their own unless you add one.

Short answer

Infinite scroll loads later items into the current page as the visitor moves, and those items have no URL of their own unless you add one.

The photograph shows the human gesture. The crawl problem is invisible in that picture: a crawler does not scroll. If the next set of products exists only after an intersection observer fires, it is absent from the fetched HTML. SEO Health asks for a linked URL for each set you want discovered.

Definition

A hybrid that keeps scroll for people and also renders page links in HTML satisfies both. A hybrid that only updates the address bar with history.pushState, without a server response for that address, creates a URL that reloads as page 1. That is a false address. Fetch it and see.

How a crawl meets this rule

Provide crawlable page URLs for sets that scroll would otherwise hide, and make sure those URLs return their own items.

Do not count the scrolled items as indexed because they appeared in a demo. Appearance in a browser session is not a fetch. The sample is a second-page URL requested with a plain HTTP GET, body inspected for the items.

What to check

  • Later items absent from the first HTML response
  • Page URLs that return those items to a plain GET
  • History URLs that reload as a different page
  • An HTML anchor to the next set
  • One second-page fetch recorded in the note

A practical example

A parts list scrolls forever on /parts. The second screen of parts has no address. Adding /parts?page=2 that returns those rows, and a link to it in the HTML, creates the path. The scroll can remain as a convenience that requests that same URL.

What this does not claim

Adding page URLs beside scroll does not guarantee rankings or citations.
