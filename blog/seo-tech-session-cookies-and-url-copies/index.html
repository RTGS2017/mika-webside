Session Cookies and Session URLs Both Split One Document

A session identifier belongs in a cookie when the document does not change per visit, not in the URL.

Short answer

A session identifier belongs in a cookie when the document does not change per visit, not in the URL.

The cookie diagram shows the id stored and sent back without becoming part of the address. A URL that contains the id is a new address every time, so canonicals, sitemaps, and caches fracture. SEO Health strips session parameters from links. The cookie is not a tracking lecture here. It is a way to avoid minting URLs.

Definition

If the HTML actually changes for each user, a cookie does not make those variants one document. Personalized pages should not be canonical public URLs. Public documents should be fetchable without the session cookie and should look the same on two clean fetches.

How this affects the indexable URL

Remove session ids from URLs and links, and confirm a cookie-free fetch still returns the public document.

A redirect that adds the session id and then canonicalizes back to the clean URL is a loop of confusion. Stop adding the id. Analytics that need a campaign code can read it once and continue on the clean URL. Internal links must not preserve the code.

What to check

  • No session id in internal links or the sitemap
  • One-hop redirects from old id URLs to the clean path
  • Cookie-free fetches that still return the public text
  • Personalized views not used as canonical URLs
  • One clean product URL fetched twice

A practical example

The store rewrites every internal link to include ;jsessionid= and the sitemap exports those URLs. Two fetches are two documents. The repair stops the rewrite, redirects any id URL to the clean path in one hop, and regenerates the sitemap from clean URLs. A cookie may still exist for the cart.

What this does not claim

Removing session URLs does not guarantee rankings or citations.
