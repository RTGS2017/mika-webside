A translation integration has to publish the same HTML facts

A localization integration is successful when the live HTML in each language shows the same company, product, specification, and application facts. A connector that moves strings while the published page drops a limit has not finished the job.

Definition

Translation software can store strings, statuses, and handoffs. Search and buyers do not read that database. They read the URL. The integration has to end in a document: one canonical URL per language, a title, and text a fetch returns. If the only correct sentence lives in the translation tool, the website is still partial. Do not add an /en/ prefix. English remains at the root and Chinese under /zh/.

Short answer

A localization integration is successful when the live HTML in each language shows the same company, product, specification, and application facts. A connector that moves strings while the published page drops a limit has not finished the job.

Fields that must say the same thing

Map fields, not vibes. Company name, product name, specification, application, claim, and question coverage should be comparable across the connected languages. A custom field that holds a slogan is not a substitute for the operating range.

The issue on the page

After publish, fetch both URLs and read the specification in the HTML. A preview inside the tool is not the crawl path. Broken links from the translated page back to the datasheet waste the path you just created. Template-level mistakes should be fixed in the template, not patched on one hero.

Signals that travel with the page

Hreflang belongs on the URLs the integration actually publishes, including a self-reference, with x-default on English. The sitemap can list those URLs after they return the intended text. The sitemap does not create the text.

The system of record for a buyer is the page, not the translation connector. Mika Visibility keeps one set of company, product, specification, and application facts in every language you publish, while the market’s own questions need real depth. English stays at the root. Chinese stays under /zh/. Do not add an /en/ prefix. Hreflang uses en, zh-Hans, and x-default pointing at the English URL. A health finding never becomes a growth score.

What to check

  • Fetch the live URL and confirm the specification is in HTML text.
  • Compare product name and units across the connected languages.
  • Fix the template if every language drops the same field.
  • Add hreflang only for URLs that already return the text.

What this does not claim

A practical example

Teaching example, not a vendor score. A connector sends the product name and a short headline into the other language and leaves the pressure rating in the source only. The live page looks integrated and cannot answer which rating applies. The repair maps the rating into the published body and re-audits the fetch. No integration brand is being ranked here.
