Lazy Loading the Hero Delays the Largest Paint

Short answer

Lazy loading the hero image delays the request for the element that often sets Largest Contentful Paint.

The comparison figure is about how much image data different lazy-load behaviors pull in, not about a score. The health point is narrower: if the largest element is deferred, its request cannot start with the document. SEO Health flags that pattern on the template. It does not publish a paint time for the figure’s example sites.

Definition

Some libraries and native lazy loading both wait until an image is near the viewport. That wait is helpful below the fold and harmful for the first screen. A template can use both behaviors if it chooses by position. A single helper that always sets lazy is how the hero gets caught.

What rendering changes for a crawler

Remove lazy loading from the image that occupies the first viewport, and let other images keep it.

Preload can be a follow-up when the hero URL is known in the head, but preload does not excuse leaving loading=lazy on the same image. The two hints disagree. The audit should show the markup, not a slogan about speed. After the attribute is gone, check one URL’s raw HTML so a component wrapper did not add it back.

What to check

  • loading=lazy on the largest first-screen image
  • A component default that cannot tell hero from grid
  • Conflicting preload and lazy hints on the same URL
  • Raw HTML after the template change
  • No invented paint time taken from the figure

A practical example

A product card component always sets lazy, and the same component is reused for the hero. The category page’s largest image therefore waits. The fix is a prop for the first instance, not a new image format. The grid of twenty cards underneath can stay lazy.

What this does not claim

Moving the hero request earlier does not guarantee rankings or citations.
