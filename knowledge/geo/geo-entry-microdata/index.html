What to check

Say the name in the body

Put the concrete name in a sentence a stranger can read without opening a menu. The first screen should state the same product name, property, and value in the paragraph and in the markup. A heading that only says “solutions” does not identify the entity, and a model number buried in a download does not help a summary that never sees the sentence.

Answer the question in one passage

The question to answer in plain language is: whether the structured fields and the visible paragraph say the same thing? One short passage should be quotable on its own. If the passage still leaves a mismatch between markup and the words a person can read, mark the coverage partial and add the missing constraint, range, or exclusion instead of another adjective.

Put evidence next to the claim

The evidence for this page is a visible specification line that matches the marked-up property. Link it with anchor text that names the destination, and make sure the target URL returns the document you mean. A claim with no openable support is not citation-ready, even if the sentence sounds confident.

Repeat the same fact in both languages

English at the site root and Chinese under /zh/ should keep the same company name, product name, specification, and application. Translation may change word order. It should not invent a second microdata or a second operating range. Hreflang marks the alternates. It does not guess which language an answer product will prefer.

A practical example

Markup that says a pressure rating the paragraph never states gives two stories. Delete the hidden value or write it in the sentence. Structured data is a hint beside the text, not a second brochure. The contrast used across Mika’s teaching material is the same kind of contrast: a page of slogans versus a page that names the company, the product family, the application, and a constraint, with a datasheet beside the claim. That scene is illustrative. It is not a customer story, and it is not a measured result.
